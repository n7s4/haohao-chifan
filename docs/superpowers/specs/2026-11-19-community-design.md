# 社区互动：发布菜谱、点赞、收藏、评论 · 设计

日期：2026-11-19 · 状态：待确认

## 意图

「好好吃饭」目前是纯个人工具：所有表按 `user_id` 隔离，自建菜只有本人可见。要把它变成**朋友圈子里的小社区**：用户可以把自建菜发布出去，所有人都能看到、点赞、收藏、评论。

## 目标

- 用户可把自建菜**发布到社区**；可随时**更新到社区**、**撤回**。
- 别人的社区菜可**收藏**（书签，在线看）或**存到我的菜谱**（复制成自己的私有菜，之后就能排计划、生成采购清单、进烹饪模式、离线使用、修改）。
- 内置 5 道菜也是社区菜，同样可点赞、评论。
- 每道社区菜：点赞（数 + 我是否赞过）、收藏（沿用现有爱心）、评论列表（昵称 + 头像）。
- 评论：纯文字，支持**一层回复**；评论者本人、菜的作者可删除评论。
- 举报：菜和评论都可举报；管理员在 Supabase 后台手动处理。
- 游客可浏览社区，点赞 / 评论 / 举报 / 发布需登录。

## 非目标（本期不做）

- 自动内容审核、敏感词过滤、图片审核（只给朋友圈子用）。
- 评论配图、评论点赞、多层楼中楼、@ 提醒、消息通知。
- 关注 / 粉丝、个人主页。
- 管理后台界面（用 Supabase Dashboard / SQL 处理）。
- 上架国内应用商店所需的合规能力。

## 反目标（技术上能跑但算失败）

- 别人发布的菜混进我的私有数据（「我的菜谱」、同步、导出备份、游客合并）。
- 改动现有私有表的 RLS、私有图片桶 `recipe-media` 的策略，或现有同步代码的行为。
- 暴露用户邮箱或邮箱前缀（例如 QQ 号）给其他人。
- 撤回 / 删除后，社区里还能通过旧链接拿到图片。

## 约束

- Supabase（project `ycjqegldhutefwhzvplc`），Expo SDK 58 / RN 0.88 / Reanimated 4 / expo-router。
- 现有同步：本地优先，云端后写赢；`src/lib/sync/pull.ts` 拉 `recipes` 时**不按 user_id 过滤**、全靠 RLS —— 这是不动私有表 RLS 的直接原因。
- 迁移按 `supabase/migrations/00N_*.sql` 编号、幂等可重复执行。
- 底部 Tab 已有 5 个位置（发现 / 计划 / 中间新建 / 收藏 / 我的），iOS 中间是「+」。

## 方案对比（已选：方案 2）

| 方案 | 做法 | 取舍 |
|---|---|---|
| 1. 现有菜谱加 `published` 标记 | 放开 `recipes` 与私有桶的读权限 | 单份数据、改了立刻生效；但同步 / 导出 / 合并等处都要补 user_id 过滤，漏一处就串数据。**否决** |
| **2. 发布时复制快照到社区（选用）** | 新表 `community_recipes` + 公开桶；发布 / 更新时复制菜谱与图片 | 私有数据与同步一行不改；代价是作者改菜后需手动「更新到社区」，图片多一份 |
| 3. 社区操作全部走 Edge Function | 服务端统一鉴权 | 最可控但代码量最大、每次多一跳，朋友圈规模用不上 |

用户选择方案 2：社区与私人数据完全隔离，发出去的就是那个版本，符合分享直觉。

## 已定的设计

### 数据（新迁移 `007_community.sql`）

- **`community_recipes`**：社区菜快照。
  - `id uuid` 主键；`author_id uuid`（内置菜为 null）；`source_recipe_id text`（作者私有菜的 id，内置菜为内置 id）；`builtin boolean`。
  - 菜谱字段与 `recipes` 对齐（name、subtitle、description、minutes、difficulty、calories、tags、art、ingredients、steps、heat、tips、step_minutes、cover）。图片路径指向公开桶。
  - `status`：`published` / `withdrawn` / `removed`（管理员下架）。
  - `like_count`、`comment_count`（触发器维护），`published_at`、`updated_at`。
  - 唯一：`(author_id, source_recipe_id)` —— 同一道私有菜只对应一条社区菜，重复发布 = 更新。
  - RLS：所有人（含 anon）可读 `status = 'published'`；作者可读写自己的行；客户端不能改 count 和 `removed` 状态。
- **`community_likes`**：`(user_id, community_recipe_id)` 主键。本人增删，所有人可读计数。
- **`community_comments`**：`id`、`community_recipe_id`、`user_id`、`parent_id`（只允许指向顶层评论，即一层回复）、`body`（1–500 字）、`deleted`（评论者或作者删除）、`hidden`（管理员隐藏）、`created_at`。*（`deleted` 与 `hidden` 分开：我的决定）*
  - 删除是软删，服务端同时把 `body` 清空，匿名用户也无法通过 API 读到原文。顶层评论删除后若有回复，显示「该评论已删除」。
  - 管理员隐藏的评论连同它的回复一起不可见。
  - 评论者本人、该菜作者可删；读权限对所有人开放（`hidden = false`）。
- **`community_reports`**：`id`、`reporter_id`、目标（菜或评论）、`reason`、`created_at`、`resolved`。只能插入，不能读别人的举报。同一人对同一目标只能举报一次。
- **`public_profiles`**：新表，`user_id`、`nickname`、`avatar_path`（公开桶）。所有人可读，本人可写。现有 `profiles` 的 RLS 不动。第一次进行社区操作时创建：设昵称，同时把已有头像复制一份到公开桶。之后换头像时一起更新。*（我的决定）*
- **收藏**：沿用 `recipe_prefs.favorite`。收藏别人的社区菜时，`recipe_id` 记为 `community:<uuid>`。这只是一个指针，不含别人的菜谱内容。
  - 内置菜在社区里收藏时，仍切换原来的内置 id（如 `tomato-pasta`）；收藏自己发布的菜时，切换自己的私有菜 id。这样同一道菜不会被收藏两次。*（我的决定）*
  - 收藏社区菜需要登录，所以游客合并不会遇到 `community:` id。备份导出照常带上这些 id，只是指针。*（我的决定）*
  - 「一键排三天」（`planThreeDays`）从收藏里挑菜时**跳过 `community:` id**。这是对计划逻辑唯一的改动。*（我的决定）*
  - 「收藏」页里的社区菜在线拉取显示；取不到（已撤回或被下架）时显示「已下架」卡片。
- **存到我的菜谱**（用户选的方案 C）：把社区菜快照连同图片（公开桶 → 私有桶）复制成一道普通自建菜，走现有的 `createRecipe`。从此与社区版本无关：作者更新或撤回都不影响这份。
  - `recipes` 加一个可空列 `origin jsonb`：`{ communityId, authorNickname }`，详情页据此显示「来自 @某某」。只加列，不动 RLS。*（我的决定）*
  - 已经存过的同一道社区菜，再点时提示「已存到我的菜谱」并跳过去，不重复复制。*（我的决定）*
  - 内置菜和自己发布的菜不显示这个按钮。
  - 曾考虑过的另外两种做法：A. 收藏只是书签，不能排计划，用不起来，否决；B. 让计划、采购、烹饪、离线都直接支持社区菜，要改计划和同步的核心代码，与方案 2 的初衷相悖，否决。

### 图片

- 新建**公开桶 `community-media`**，只允许图片，大小限制与 `recipe-media` 一致，路径为 `{community_recipe_id}/{imageId}.jpg`。只复制封面和步骤图；App 不存视频（视频只用来截帧配图），所以快照里也没有视频。*（我的决定）*
- 发布 / 更新：把私有桶里的封面和步骤图复制到公开桶（`storage.copy` 不支持跨桶的话，就下载后再上传；在客户端做）。
- 撤回 / 删除：删掉公开桶里这道菜的整个目录。
- 头像：设置头像时，同时往公开桶写一份到 `avatars/{userId}.jpg`。

### 界面

- **入口**：在「发现」页顶部加分段切换「菜谱 / 社区」，**不新增第 6 个 Tab**。现有 Tab 栏已满，中间还有「+」，再加一个会挤。社区列表沿用发现页的双列卡片（`RecipeTile`），卡片右下角显示点赞数和评论数，可按「最新 / 最热」切换。
- **社区菜详情**：复用菜谱详情页的布局。顶部显示作者头像和昵称；底部操作栏放 赞 / 收藏 / 评论；正文下方是评论区，评论框固定在底部。
- **我的菜谱详情**：「…」菜单里加「发布到社区」。已发布的菜显示「已发布」标记，菜单项变成「更新到社区」「撤回」。
- **撤回 / 重新发布 / 删除** *（我的决定）*：
  - 撤回是软操作：`status` 改为 `withdrawn`，删掉公开桶里的图片，点赞、评论、收藏都保留。
  - 重新发布时更新同一行、重新上传图片，点赞、评论、收藏随之恢复。
  - 私有菜被删除（`recipes.deleted` 变为 true，不论从哪台设备）时，由 `recipes` 上的**数据库触发器**把对应社区菜置为 `withdrawn`，不改同步代码。公开桶的图片在作者下一次打开 App 时由客户端清理。
  - 不做硬删除；只有账号注销时级联删除。
- **作者撤回或删除后**：别人收藏里这道菜显示「已下架」卡片，样式参照计划页的「这道菜暂时取不到」；评论不再可见。已经「存到我的菜谱」的那份不受影响。
- **内置菜的作者**显示为「好好吃饭」。
- **昵称**：第一次进行社区操作（发布、评论）时，弹出设置昵称；默认值为「吃饭的人」+ 4 位随机数，**不使用邮箱**。昵称和头像在「我的 → 账号」页可以修改。
- **举报**：社区菜详情页的「…」菜单，以及长按评论，都可以举报，原因从「广告 / 不友善 / 不相关 / 其他」中选。

### 管理（手动）

- 管理员在 Supabase Dashboard 查看 `community_reports`，下架菜谱时把 `status` 改为 `removed`，隐藏评论时把 `deleted` 设为 true。
- 设计文档附一份常用 SQL 片段（查看未处理举报、下架、隐藏评论）。
