# 关注、个人主页与私信/群聊 设计

日期：2026-11-20
状态：待用户最终确认

## 为什么做

把社区做活，让陌生用户通过做菜互相认识。现在社区只能看菜、点赞、评论，点作者进不去任何地方，看到喜欢的人也没法继续联系。

## 目标

- 社区里任何一个头像或昵称都能点进对方主页，主页上可以关注对方。
- 能给别人发私信；对陌生人有防骚扰限制。
- 能把互相关注的人拉进私人群聊。
- 被骚扰时有拉黑和举报可用。

## 非目标

- 公开话题群（任何人可搜可加的群）：等社区人多了再做。
- 手机系统推送（App 没开时弹通知）：要配 FCM 并重新打包，留到下一次打包时做。这期只做 App 内的消息列表和红点。
- 消息里发图片、语音、菜谱卡片：这期只发文字。
- 「已读」回执、正在输入、消息搜索、撤回消息。

## 反目标（做出来但等于失败）

- 私信变成骚扰通道：陌生人可以无限给人发消息，或者被拉黑的人还能继续发。
- 拉黑会暴露给对方：被拉黑的人能明确看出自己被拉黑了。
- 消息延迟明显：两个人都开着聊天页时，消息要几秒内出现，而不是要手动刷新。

## 约束

- 后端只用现有的 Supabase：Postgres + RLS + Realtime。不引入第三方 IM。
- 不加原生模块，不改 package.json scripts，两期都必须能通过 OTA 热更新上线（见 OTA 指纹约束）。
- 所有社交功能都需要登录；游客点关注、私信时走现有的登录引导。
- 生产库迁移必须先由用户确认后再执行。
- 权限规则写在数据库（RLS / 触发器）里，不能只靠客户端检查；用 pgTAP 测。

## 方案选择

| 方案 | 取舍 |
|---|---|
| **A. 全用 Supabase**（选定） | 消息存 Postgres，RLS 管权限，Realtime 订阅做实时；能热更新、和现有社区同一套测试方式。代价是未读数、防骚扰规则都要自己写。 |
| B. 第三方 IM SDK（腾讯云 IM / Stream） | 功能现成，但要原生模块重新打包、按月活收费、用户关系要两边同步、聊天内容存在第三方。 |
| C. 只用 Realtime 广播不落库 | 离线消息会丢，做不成聊天，排除。 |

群聊用户选定**私人群**：只能拉自己互关的人，不做公开群。

## 分期

两期分别上线，每期单独可用。

### 第一期：关注、个人主页、拉黑

**数据**

- `follows(follower_id, followee_id, created_at)`，主键是这两列，不能关注自己。
- `blocks(blocker_id, blocked_id, created_at)`，主键是这两列，不能拉黑自己。
- `community_reports` 增加 `reported_user_id` 目标（举报用户），沿用「每个目标只能举报一次」的规则。

**规则（数据库强制）**

- 只能以自己的身份关注和取关。
- 任意一方拉黑了另一方时，双方都不能关注对方；拉黑时自动删除双方之间已有的关注关系。
- 关注列表、粉丝列表对所有登录用户可见（和社区公开资料一致）。
- 拉黑关系只有拉黑者自己能看到。
- 被拉黑的一方去关注拉黑者时，统一提示「暂时无法关注」，不说明原因。（实现者决定）
- 关注数、粉丝数和列表用 RPC 或视图实时算，不加冗余计数列；不做隐私开关。（实现者决定）

**界面**

- 看自己的主页时「编辑昵称」复用现在的 NicknameSheet。
- 新页面 `/user/[id]` 用户主页：头像、昵称、关注数、粉丝数、Ta 发布到社区的菜谱（只列已发布的）；按钮「关注 / 已关注 / 互相关注」；右上角「···」里有拉黑、举报。看自己的主页时没有这些按钮，改为「编辑昵称」。
- 新页面：关注列表、粉丝列表，每行带关注按钮。
- 入口：社区菜谱详情页的作者行、评论里的头像和昵称，点了都进主页。「我的」页显示自己的关注数和粉丝数，点进列表。
- 拉黑后：对方的社区菜谱和评论在我这边不再显示（客户端过滤）。「我的」页里有「黑名单」可以解除。

### 第二期：私信和私人群聊

**数据**

- `conversations(id, kind, name, owner_id, created_at, last_message_at)`，`kind` 是 `direct` 或 `group`。私信就是只有两个成员的会话；同一对用户只有一个 direct 会话。
- `conversation_members(conversation_id, user_id, role, joined_at, last_read_at)`，`role` 是 `owner` 或 `member`。
- `messages(id, conversation_id, sender_id, body, created_at)`，`body` 1–1000 字的纯文字。
- `community_reports` 增加 `message_id` 目标（举报消息），举报时把消息正文存一份快照。举报只入库，管理员在 Supabase 后台处理，没有管理界面。同一人对同一目标只能举报一次，沿用现有唯一索引的做法。（实现者决定）
- 三张表加入 `supabase_realtime` publication；`last_message_at` 由插入消息的触发器维护。本地 Supabase 已启用 Realtime。

**规则（数据库强制）**

- 只有会话成员能读这个会话和它的消息，只有成员能发消息，发送者必须是自己。
- 开私信：通过一个数据库函数「找到或创建和某人的私信」，双方任意一方拉黑了对方就失败。
- 陌生人限制：只对私信会话生效，按会话计。只要对方在这个会话里发过任何一条消息，就永久不再限制；否则看对方「当前」是否关注我：关注就不限制，没关注（包括后来取关）就最多 1 条。我关注对方不影响限制。（实现者决定）
- 被拉黑：被拉黑的人发私信失败，提示统一写「对方暂时无法接收消息」，不说明是被拉黑。
- 群聊：建群人是群主。任何成员都能邀请人，但只能邀请和自己互相关注、且双方没有拉黑关系的人。群主能改群名、移除成员。成员可以退群；群主退群时群主转给最早入群的成员；最后一个人退出后会话删除。
- 群人数上限 50。
- 发消息频率上限：每人每分钟 30 条，跨所有会话合计。人数上限和频率上限用触发器计数即可，并发下偶尔多出一两条可以接受。（实现者决定）
- 账号删除（数据库里 auth.users 被删）时：成员关系随之删除；消息保留，发送者显示为「已注销用户」（sender_id 置空）。目前 App 没有注销功能，这条只是保证外键行为合理。（实现者决定）

**未读和实时**

- 每个成员的 `last_read_at` 记录读到哪；未读数 = 会话里晚于 `last_read_at`、且不是自己发的消息条数。
- 进入聊天页时订阅这个会话的新消息（Realtime postgres_changes，按 conversation_id 过滤，受 RLS 约束）。
- 消息列表页和红点：App 回到前台、打开消息列表时拉取一次；在消息列表页时订阅自己所在会话的变化。
- 拉黑对已有联系的影响（用户选定）：
  - 已有的私信会话保留，但被拉黑的一方再发消息由数据库拒绝，提示「对方暂时无法接收消息」；拉黑者仍可查看历史。解除拉黑后恢复正常。
  - 双方同在的群继续保留，双方都能在群里发言。拉黑者看不到被拉黑者在群里的消息（客户端过滤）；被拉黑者照常看到拉黑者的消息，因此察觉不到被拉黑。
  - 拉黑后不能再把对方邀请进群（双方任一方邀请都被拒绝）。

**界面**

- 新页面 `/messages` 消息列表：每行是一个会话（对方头像昵称或群名）、最后一条消息预览、时间、未读数。右上角「发起群聊」。
- 新页面 `/messages/[id]` 聊天页：气泡列表、底部输入框（键盘处理沿用现在评论输入框的做法）。陌生人限制触发时，输入框上方提示「对方回复或关注你之前，只能发送 1 条消息」。群聊右上角进群设置：成员列表、邀请、改群名、移除成员、退群。
- 长按别人的消息：举报。不做「复制」：项目没装 expo-clipboard，装了就要重新打包，留到下次打包和系统推送一起做。（实现者决定）
- 入口：用户主页的「私信」按钮；发现页社区模式顶部的消息图标（有未读时显示红点）；「我的」页的「消息」入口。
- 发起群聊：从互相关注列表里多选，至少选 2 人。

## 测试

- pgTAP：每条「数据库强制」规则都要有正反两面的测试（能做的能做到、不能做的被拒绝）。
- Deno 单测：未读数计算、按钮状态（关注 / 已关注 / 互相关注）、陌生人限制提示的判断这类纯逻辑。
- 集成测试（`COMMUNITY_IT=1`，连本地 Supabase）：关注 → 互关 → 私信 → 建群 → 邀请 → 退群的完整流程；拉黑后私信失败。

## 留给实现者决定

- 页面的具体布局、配色、动画，沿用 App 现有风格。
- 主页上菜谱的排列方式（网格还是列表）。
- 消息分页大小、聊天页加载更早消息的方式。
- 未读数是用视图、RPC 还是客户端算，只要结果正确、一次请求拿到整个列表。
- 迁移文件拆分方式（建议每期一个：009、010）。
